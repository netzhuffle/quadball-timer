# SQM Controller code-sharing research

Research date: 16 August 2026  
Scope: the current local checkout; read-only review of source code, `CONTEXT.md`, ADRs, and local agent documentation. No tests or qualification workloads were run.

## Executive answer

For an SQM-ready Controller in roughly eight hours, keep the Event Game Controller as the production UI and durable authority, but put its post-admission traffic onto a shared Controller WebSocket connection lifecycle. The high-velocity architecture is:

1. keep `EventGameControllerPage`, `controller-reconnect.ts`, typed Grant authority, `EventGameRecord`, and Foundation acceptance as the Event-specific production path;
2. generalize the existing `/ws` connection lifecycle and outer message envelope so it can bind either an Ad Hoc Controller session or an Event Grant Session, while dispatching `GameCommand` and `LiveEventControllerIntent` to their existing owners;
3. broadcast each committed Event projection to every Controller bound to that Event Game and continue feeding the existing Event audience projection stream;
4. treat `controller-synchronization.ts`, the `IqaSportingRules` facade, socket lifecycle, shared validation/color primitives, and DTO-neutral visual primitives as the reuse boundary;
5. do not attempt a unified Controller command schema or shared persistence adapter in the SQM window.

This is an inference from the current seams plus the fixed SQM requirement that all post-open Controller traffic use WebSockets: the two pages, command languages, authority paths, and persistence models are separate, while causal ordering and the policy-neutral IQA facade are explicitly shared and the existing `/ws` handler already owns socket connection/subscription lifecycle. ([src/pages/game-page.tsx:L6-L35](../../src/pages/game-page.tsx#L6-L35), [src/pages/event-game-controller-page.tsx:L12-L55](../../src/pages/event-game-controller-page.tsx#L12-L55), [src/lib/controller-synchronization.ts:L3-L25](../../src/lib/controller-synchronization.ts#L3-L25), [src/lib/iqa-game-rules.ts:L4-L20](../../src/lib/iqa-game-rules.ts#L4-L20), [src/index.ts:L2331-L2454](../../src/index.ts#L2331-L2454))

The current domain boundary also supports keeping the workflows asymmetric: an Event Game has durable accepted Control Actions and rebuilt Derived Game State, whereas an Ad Hoc Game is controller-only, has no spectator experience or durable Control Audit Trail, and is independently quota-managed. ([CONTEXT.md:L308-L317](../../CONTEXT.md#L308-L317))

## What is already shared

### Causal replay infrastructure

`controller-synchronization.ts` defines one workflow discriminator for `event` and `ad-hoc`, one operation shape with operation identity, client-origin time, causal predecessors, and payload, and shared replay validation/acknowledgement types. Its topological ordering is explicitly used by both policy layers. ([src/lib/controller-synchronization.ts:L3-L25](../../src/lib/controller-synchronization.ts#L3-L25), [src/lib/controller-synchronization.ts:L79-L148](../../src/lib/controller-synchronization.ts#L79-L148), [src/lib/controller-synchronization.ts:L206-L298](../../src/lib/controller-synchronization.ts#L206-L298))

The Ad Hoc service uses that infrastructure to parse and order `GameCommand` replay operations, then rebuilds its state from the accepted operation set. ([src/lib/ad-hoc-games.ts:L2412-L2473](../../src/lib/ad-hoc-games.ts#L2412-L2473), [src/lib/ad-hoc-games.ts:L2508-L2524](../../src/lib/ad-hoc-games.ts#L2508-L2524), [src/lib/ad-hoc-games.ts:L2544-L2575](../../src/lib/ad-hoc-games.ts#L2544-L2575)) The Event browser replica uses the same causal concepts but keeps Event-specific statuses, session binding, replica generation, and unacknowledged batch identity. ([src/lib/controller-reconnect.ts:L75-L121](../../src/lib/controller-reconnect.ts#L75-L121), [src/lib/controller-reconnect.ts:L301-L357](../../src/lib/controller-reconnect.ts#L301-L357))

Recommendation: this is the safest immediate sharing seam. Extend it only with generic replay helpers or types; do not make either workflow accept the other workflow's payload.

### IQA rule facade, not a shared state model

`iqa-game-rules.ts` exposes a policy-neutral `apply`/`project` facade over the legacy `GameState`/`GameCommand` engine, and the default implementation is `game-engine.ts`. ([src/lib/iqa-game-rules.ts:L4-L20](../../src/lib/iqa-game-rules.ts#L4-L20)) The Event interpreter also selects the default IQA sporting rules while rebuilding Event-derived state from Event roots and canonical actions. ([src/lib/live-event-game-control.ts:L666-L680](../../src/lib/live-event-game-control.ts#L666-L680))

This is already shared interpretation policy, but not a shared authoritative representation. Ad Hoc applies `GameCommand` to `GameState`; Event derives a `ControllerProjection` from `EventGameRecordRoot` and stored `ControlAction`s. ([src/lib/ad-hoc-games.ts:L2544-L2575](../../src/lib/ad-hoc-games.ts#L2544-L2575), [src/lib/live-event-game-control.ts:L297-L310](../../src/lib/live-event-game-control.ts#L297-L310)) Replacing Event intents with `GameCommand` would discard or re-encode Event-specific facts, corrections, clock authority, suspensions, presentation changes, and audit provenance.

### Shared low-level policy and UI primitives

Both workflows use the common validation policy through their owning modules, and both pages use the shared React UI primitives such as `Button`, `Card`, `Input`, and `Label`. The Ad Hoc page additionally has reusable Controller presentation components (`ControllerTopSection`, `PenaltyColumnsSection`, and `GameControllerActionPanels`), while the Event page currently renders its Event-specific Controller surface directly. ([src/pages/game-page.tsx:L1-L9](../../src/pages/game-page.tsx#L1-L9), [src/pages/event-game-controller-page.tsx:L1-L5](../../src/pages/event-game-controller-page.tsx#L1-L5), [src/components/game-controller-sections.tsx:L87-L87](../../src/components/game-controller-sections.tsx#L87-L87), [src/components/game-controller-sections.tsx:L411-L411](../../src/components/game-controller-sections.tsx#L411-L411), [src/components/game-controller-action-panels.tsx:L32-L32](../../src/components/game-controller-action-panels.tsx#L32-L32))

This makes visual extraction possible, but the existing components are not a current cross-workflow Controller module: the Ad Hoc page supplies `GameState`-shaped values and `GameCommand` callbacks, while the Event page supplies `ControllerProjection` values and intent/replay callbacks. ([src/pages/game-page.tsx:L882-L930](../../src/pages/game-page.tsx#L882-L930), [src/pages/event-game-controller-page.tsx:L1828-L1865](../../src/pages/event-game-controller-page.tsx#L1828-L1865), [src/pages/event-game-controller-page.tsx:L2284-L2335](../../src/pages/event-game-controller-page.tsx#L2284-L2335))

## What can be shared quickly

These are bounded, low-risk seams because they do not require changing either authority or persistence model:

- **Causal operation metadata and topology.** Reuse `ControllerSynchronizationOperation`, replay envelope validation, topological ordering, and retry projection. Keep `payload` owned by each workflow. ([src/lib/controller-synchronization.ts:L20-L30](../../src/lib/controller-synchronization.ts#L20-L30), [src/lib/controller-synchronization.ts:L72-L148](../../src/lib/controller-synchronization.ts#L72-L148))
- **Rule-policy vocabulary.** Keep `DEFAULT_IQA_SPORTING_RULES` as the shared policy-neutral facade, but let Ad Hoc continue to apply `GameCommand` and Event continue to interpret canonical Event actions. ([src/lib/iqa-game-rules.ts:L4-L20](../../src/lib/iqa-game-rules.ts#L4-L20), [src/lib/live-event-game-control.ts:L666-L680](../../src/lib/live-event-game-control.ts#L666-L680), [src/lib/ad-hoc-games.ts:L2563-L2575](../../src/lib/ad-hoc-games.ts#L2563-L2575))
- **Small visual primitives and shell behaviors.** Reuse generic cards, buttons, labels, color helpers, formatting helpers, and—only where props can be made DTO-neutral—extract a clock/score/penalty display. The current Controller action components are not DTO-neutral, so this is presentation refactoring rather than backend sharing. ([src/pages/game-page.tsx:L1-L35](../../src/pages/game-page.tsx#L1-L35), [src/pages/event-game-controller-page.tsx:L1-L55](../../src/pages/event-game-controller-page.tsx#L1-L55), [src/pages/event-game-controller-page.tsx:L1641-L1665](../../src/pages/event-game-controller-page.tsx#L1641-L1665))

Reuse the signal contract, not the stores or sockets. ## Sharing that requires significant extra effort

### One unified Controller command language

This would require a real translation/domain migration, not a type alias. Ad Hoc commands use `home`/`away` and mutate a mutable `GameState`; Event intents target stable Event Game Side IDs and carry immutable fact/correction/audit-oriented fields. Event also has clock generation and Offline Clock Holder rules, heat stoppage and suspension snapshots, and presentation changes. ([src/lib/game-types.ts:L80-L219](../../src/lib/game-types.ts#L80-L219), [src/lib/live-event-game-control.ts:L97-L212](../../src/lib/live-event-game-control.ts#L97-L212), [CONTEXT.md:L91-L112](../../CONTEXT.md#L91-L112))

The migration would need bidirectional adapters, stable identity mapping, lifecycle guards, correction semantics, clock authority rules, and separate audit provenance. It risks weakening the Event record if it accepts an Ad Hoc-shaped snapshot or command. The smallest safe choice is to retain two payload languages and share only the envelope/topology layer.

### One shared persistence adapter

The Ad Hoc store is a quota-prunable document-like store with state and operation JSON, while Event persistence is a foundation-backed record/action/audit/grant system with transactional acceptance and replay receipts. ([src/lib/ad-hoc-games.ts:L140-L187](../../src/lib/ad-hoc-games.ts#L140-L187), [src/lib/ad-hoc-games.ts:L1571-L1582](../../src/lib/ad-hoc-games.ts#L1571-L1582), [src/lib/event-game-record.ts:L227-L244](../../src/lib/event-game-record.ts#L227-L244), [src/lib/foundation-acceptance.ts:L1145-L1185](../../src/lib/foundation-acceptance.ts#L1145-L1185)) A common repository would either encode the richer Event guarantees into Ad Hoc or make Event persistence conditional and unsafe. That is a multi-day boundary redesign, not an SQM acceleration.

### One shared Controller WebSocket envelope is bounded but nontrivial

The current `/ws` protocol has `subscribe-game`, `apply-commands`, and `game-snapshot` messages shaped around Ad Hoc `GameCommand`; it explicitly accepts only the `ad-hoc` workflow in command envelopes. ([src/lib/ws-protocol.ts:L14-L46](../../src/lib/ws-protocol.ts#L14-L46), [src/lib/ws-protocol.ts:L169-L277](../../src/lib/ws-protocol.ts#L169-L277)) The server's socket session state and subscription handling are likewise split between Ad Hoc game subscriptions and public Event subscriptions; Event Controller routes are HTTP endpoints for open, intent, replay, refresh, switch, stay, QR reveal, and leave. ([src/index.ts:L121-L145](../../src/index.ts#L121-L145), [src/index.ts:L714-L761](../../src/index.ts#L714-L761), [src/index.ts:L2331-L2454](../../src/index.ts#L2331-L2454))

Making Event Controllers use this WebSocket requires socket-bound Grant Session authorization, Event-specific admission and reassignment handling, durable replay acknowledgements, and projection fan-out. Those are real additions, but they can remain adapters around the existing Event control/replay owners rather than a command or persistence rewrite. Because SQM explicitly requires multiple synchronized Controllers and WebSocket-only post-open control, this bounded transport adaptation is must-do; generalized backpressure tuning and a deeper protocol unification can wait. The current Event foreground/reconnect and replay contract can be moved behind the socket without changing its durable semantics. ([src/pages/event-game-controller-page.tsx:L279-L297](../../src/pages/event-game-controller-page.tsx#L279-L297), [src/pages/event-game-controller-page.tsx:L1400-L1436](../../src/pages/event-game-controller-page.tsx#L1400-L1436))

### Ad Hoc spectator real time

The Event spectator path is a complete separate pipeline: the projection reader allowlists published Event data, the stream maintains versions and replaceable updates, and the WebSocket hub fans out one authoritative Event feed with spectator capacity controls. ([src/lib/audience-projection.ts:L233-L312](../../src/lib/audience-projection.ts#L233-L312), [src/lib/public-event-stream.ts:L101-L162](../../src/lib/public-event-stream.ts#L101-L162), [src/lib/public-audience-event-websocket.ts:L107-L149](../../src/lib/public-audience-event-websocket.ts#L107-L149)) Adding that to Ad Hoc would contradict the current controller-only contract and require a new public projection/privacy, lifecycle, capacity, and routing surface. Defer it.

## Smallest SQM-ready architecture

### Must-do in the SQM window

- **Treat the Event stack as the production Controller.** Its runtime is already composed from durable SQLite foundation storage, typed Grant authority, Foundation acceptance, Event Game Records, and the Event control transport. ([src/lib/live-event-game-runtime.ts:L138-L171](../../src/lib/live-event-game-runtime.ts#L138-L171), [src/lib/live-event-game-runtime.ts:L217-L342](../../src/lib/live-event-game-runtime.ts#L217-L342), [src/index.ts:L395-L419](../../src/index.ts#L395-L419))
- **Add an Event Controller binding to the shared `/ws` lifecycle.** HTTP may bootstrap/open control, but intent, presentation, replay, refresh/reauthorization, switch/stay/leave, acknowledgements, and committed projections must use the Controller socket afterward. Dispatch Event payloads to the existing Event control and replay owners; do not translate them into `GameCommand`. ([src/lib/ws-protocol.ts:L14-L46](../../src/lib/ws-protocol.ts#L14-L46), [src/index.ts:L714-L761](../../src/index.ts#L714-L761), [src/index.ts:L2331-L2454](../../src/index.ts#L2331-L2454))
- **Fan committed Event projections out to every authorized Controller and the existing audience stream.** Controller sockets receive the private `ControllerProjection`; spectators continue to receive the allowlisted `AudienceProjection`, never Grant, audit, or private workflow details. ([src/lib/live-event-game-control.ts:L3208-L3297](../../src/lib/live-event-game-control.ts#L3208-L3297), [src/lib/audience-projection.ts:L233-L312](../../src/lib/audience-projection.ts#L233-L312), [src/lib/public-audience-event-websocket.ts:L107-L149](../../src/lib/public-audience-event-websocket.ts#L107-L149))
- **Preserve the Event browser replica/replay contract.** It validates and persists a durable local replica, retains pending actions, binds them to Event Game/session/generation, and retries through `/api/event-control/replay`; Event replay re-authorizes the current bearer and checks the expected Grant Session/version before processing. ([src/lib/controller-reconnect.ts:L164-L220](../../src/lib/controller-reconnect.ts#L164-L220), [src/lib/controller-reconnect.ts:L301-L357](../../src/lib/controller-reconnect.ts#L301-L357), [src/lib/live-event-game-control.ts:L2784-L2883](../../src/lib/live-event-game-control.ts#L2784-L2883))
- **Keep the Event acceptance transaction authoritative.** Accepted actions update durable action identity, record metadata, Control Audit Trail, Grant Audit Trail, and lifecycle in the existing acceptance boundary; projections are rebuilt after reading the committed record. ([src/lib/foundation-acceptance.ts:L1111-L1185](../../src/lib/foundation-acceptance.ts#L1111-L1185), [src/lib/live-event-game-control.ts:L3208-L3297](../../src/lib/live-event-game-control.ts#L3208-L3297))
- **Keep Event spectator delivery on its existing projection stream.** The live runtime already converts the Controller projection into allowlisted audience input, and the server composes that with the published Event catalog and public WebSocket hub. ([src/lib/live-event-game-runtime.ts:L46-L135](../../src/lib/live-event-game-runtime.ts#L46-L135), [src/lib/audience-projection.ts:L366-L429](../../src/lib/audience-projection.ts#L366-L429), [src/index.ts:L338-L363](../../src/index.ts#L338-L363))
- **Share only generic helpers with Ad Hoc.** If time permits, extract DTO-neutral visual components and add generic synchronization helpers; do not route Ad Hoc actions through Event authority or Event actions through the Ad Hoc WebSocket. ([src/lib/controller-synchronization.ts:L150-L204](../../src/lib/controller-synchronization.ts#L150-L204), [src/index.ts:L2474-L2517](../../src/index.ts#L2474-L2517))

### Defer

- unified `GameCommand`/`LiveEventControllerIntent` payloads;
- collapsing Event and Ad Hoc authority, replay owners, or projection DTOs behind one generic domain service;
- a common Ad Hoc/Event persistence interface or schema;
- Ad Hoc spectators, public Ad Hoc links, event-like publication, or an Ad Hoc audience projection;
- extracting the entire Event Controller page into the legacy Ad Hoc page or vice versa;
- broad domain-model consolidation while the Event Record, Grant, and audit boundaries are already production-shaped.

These deferrals follow from the current source boundaries and the explicit Ad Hoc controller-only/Event spectator distinction, rather than from a claim that the features are impossible. ([CONTEXT.md:L316-L337](../../CONTEXT.md#L316-L337), [src/lib/ws-protocol.ts:L14-L46](../../src/lib/ws-protocol.ts#L14-L46), [src/lib/event-game-record.ts:L227-L244](../../src/lib/event-game-record.ts#L227-L244))

## Bottom line

The fastest SQM path is one shared Controller connection lifecycle and synchronization envelope, not one merged domain implementation. Keep Event-specific Grant authority, immutable durable record, projection, and replay semantics; place them behind the same WebSocket lifecycle pattern Ad Hoc already uses, and broadcast each committed Event projection to all authorized Controllers plus the existing public audience stream. Defer merging payload languages, state models, and persistence.
